This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Sunbird-ED Installer is an infrastructure-as-code project that deploys the Sunbird Education platform on Kubernetes clusters across multiple cloud providers (Azure, AWS, GCP). The deployment uses Terraform/Terragrunt for infrastructure provisioning and Helm charts for application deployment, organized into modular "building blocks" (BB).

## Architecture

### Building Block (BB) Structure

The platform is decomposed into independently deployable building blocks:

- **edbb**: Education building block - Core education services (bot, discussionmw, echo, knowledgemw)
- **learnbb**: Learning building block - Learning services, auth, user management (Keycloak, Kong, nodebb, player, lms, userorg)
- **knowledgebb**: Knowledge building block - Content management services (content, dial, learning, flink)
- **obsrvbb**: Observability building block - Analytics and data pipelines (Druid, Flink, ETL jobs, dataproducts)
- **inquirybb**: Inquiry building block - Search and discovery services
- **monitoring**: Monitoring stack (Prometheus, Grafana, Loki, Promtail)
- **additional**: Additional utilities (Velero backups, volume-autoscaler)

Each building block is deployed as a Helm umbrella chart with dependencies on both Bitnami charts (Redis, Kafka, Cassandra, PostgreSQL, Elasticsearch) and custom service charts.

### Multi-Cloud Support

The codebase supports Azure, GCP, and AWS through:

1. **Cloud-specific Terraform modules**: Located in `terraform/<cloud-provider>/`
2. **Conditional Helm templating**: Uses `.Values.global.cloud_storage_provider` to render cloud-specific configurations
3. **Service account annotations**: Cloud-specific workload identity configurations (e.g., `iam.gke.io/gcp-service-account` for GCP)

## Installation Flow

The main installation is orchestrated by `terraform/<cloud-provider>/template/install.sh`:

1. **create_tf_backend**: Initialize Terraform remote state backend
2. **backup_configs**: Backup existing kubeconfig and rclone.conf
3. **create_tf_resources**: Provision cloud infrastructure (network, storage, Kubernetes cluster, service accounts, keys)
4. **install_helm_components**: Deploy building blocks in order: monitoring → edbb → learnbb → knowledgebb → obsrvbb → inquirybb → additional
5. **certificate_keys**: Generate RSA key pairs for certificate signing (during learnbb installation)
6. **post_install_nodebb_plugins**: Activate and rebuild NodeBB forum plugins
7. **certificate_config**: Inject certificate public keys into registry-service
8. **dns_mapping**: Wait for DNS propagation (20 minute timeout)
9. **generate_postman_env**: Create Postman environment file from cluster ConfigMaps
10. **run_post_install**: Execute Postman collection to seed initial data and default users
11. **create_client_forms**: Create client-specific form configurations

### Key Installation Commands

```bash
# Full installation (from terraform/<cloud-provider>/<env>/)
time ./install.sh

# Destroy infrastructure
time ./install.sh destroy_tf_resources

# Re-run specific stages after DNS propagation
./install.sh dns_mapping
./install.sh generate_postman_env
./install.sh run_post_install
```

## Configuration Management

### Global Configuration Files

- **terraform/<cloud-provider>/<env>/global-values.yaml**: Primary configuration file containing:
  - Cloud provider settings
  - Domain and SSL certificates
  - OAuth credentials (Google)
  - Email/SMS provider settings
  - Database passwords
  - API tokens (YouTube, MSG91)

- **helmcharts/global-resources.yaml**: Resource limits/requests for all services
- **helmcharts/images.yaml**: Container image tags for all services

### Configuration Hierarchy

Helm charts are deployed with this value precedence (highest to lowest):
1. `<building-block>/ed-values.yaml` (if exists)
2. `images.yaml`
3. `global-resources.yaml`
4. `global-values.yaml`
5. `global-cloud-values.yaml` (generated by Terraform)
6. `<building-block>/values.yaml`

## Helm Chart Development

### Creating a New Service Chart

1. Add the base chart repository:
   ```bash
   helm repo add nimbushub https://nimbushubin.github.io/helmcharts/
   ```

2. Download and customize base chart:
   ```bash
   cd helmcharts/<building-block>/charts/
   helm repo update nimbushub
   helm fetch --untar nimbushub/base -d .
   # Update Chart.yaml: name, appVersion
   mv base <service-name>
   ```

3. **Do not modify templates/** - All configurations go in `values.yaml` and `configs/` folder

### Testing Helm Charts

```bash
# Update dependencies
helm dependency update ./<building-block>

# Test rendering
helm template test ./<building-block>

# Install a building block manually
helm dependency build <building-block>
helm upgrade -i <release-name> ./<building-block>
```

### Multi-Cloud Helm Templating

Use conditional logic for cloud-specific values:

```yaml
{{- if eq .Values.global.cloud_storage_provider "aws" }}
  # AWS specific config
{{- else if eq .Values.global.cloud_storage_provider "gcp" }}
  # GCP specific config
{{- else }}
  # Azure specific config (default)
{{- end }}
```

### Adding a New Cloud Provider

See `Adding Support for New Cloud Provider.md` for detailed instructions. Key steps:

1. Create `terraform/<cloud-provider>/` with modules and _common directory
2. Copy and adapt `global-values.yaml` and `install.sh` from Azure template
3. Add `cloud_provider: "<provider>"` variable
4. Update Helm charts with cloud-specific conditionals
5. Configure service account annotations for workload identity

## Important Notes

### Certificate Management

During learnbb installation, the installer:
1. Generates RSA key pairs for certificate signing
2. Stores keys in `global-values.yaml` as `CERTIFICATE_PRIVATE_KEY`, `CERTIFICATE_PUBLIC_KEY`
3. Injects public key into registry-service via nodebb pod
4. Must delete existing `keycloak-kids-keys` job before regenerating

### Default Users

Post-installation creates default users (all @yopmail.com):
- admin / Admin@123
- contentcreator / Creator@123
- contentreviewer / Reviewer@123
- bookcreator / Bookcreator@123
- bookreviewer / BookReviewer@123
- user1 / User1@123
- user2 / User2@123

### Backup Behavior

The installer backs up existing configurations with timestamps:
- `~/.kube/config` → `~/.kube/config.<timestamp>`
- `~/.config/rclone/rclone.conf` → `~/.config/rclone/rclone.conf.<timestamp>`

## Troubleshooting

### DNS Propagation Timeout

If DNS mapping times out after 20 minutes:
```bash
./install.sh dns_mapping
./install.sh generate_postman_env
./install.sh run_post_install
```

### Pod Stability Check

The installer waits for pods to be stable for 100 seconds before proceeding. It automatically removes orphaned pods (not Running/Completed).

### Keycloak Keys Job

If `keycloak-kids-keys` job already exists, it must be deleted before learnbb installation.

## Security Considerations

### GCP Security

**KMS Encryption (REQUIRED)**
- Kubernetes secrets must be encrypted with Cloud KMS
- Variable `secrets_encryption_kms_key` has validation requiring a KMS key
- Create KMS key: `gcloud kms keyrings create [KEYRING] --location [LOCATION] && gcloud kms keys create [KEY] --keyring [KEYRING] --location [LOCATION] --purpose encryption`

**Private Cluster Configuration**
- `enable_private_nodes` defaults to `true` (nodes have private IPs only)
- `disable_public_endpoint` can be enabled for fully private clusters
- `master_ipv4_cidr_block` defaults to `172.16.0.0/28` for private master

**Storage Bucket Permissions**
- Public buckets use `roles/storage.objectViewer` (read-only) with `allUsers`
- Private buckets use service account with bucket-level `roles/storage.objectAdmin`
- Project-wide `roles/storage.admin` has been removed for least privilege
- Uniform bucket-level access enabled on all buckets

**OAuth Scopes**
- GKE nodes use specific scopes instead of `cloud-platform`:
  - `devstorage.read_only`, `logging.write`, `monitoring`, `servicecontrol`, `service.management.readonly`, `trace.append`

**Firewall Rules**
- HTTP/HTTPS access configurable via `allowed_http_https_sources` variable
- Defaults to `0.0.0.0/0` (open internet) - restrict in production
- Consider using Cloud Armor for DDoS protection

**Service Account Keys**
- Service account key creation is disabled by default (commented out)
- Use Workload Identity instead of downloading keys
- If keys are required, use Secret Manager or Vault

**Logging and Monitoring**
- GKE logging enabled: `logging.googleapis.com/kubernetes`
- GKE monitoring enabled: `monitoring.googleapis.com/kubernetes`

### Azure Security

**Storage Accounts**
- `https_traffic_only_enabled` set to `true` (enforces HTTPS)
- `min_tls_version` set to `TLS1_2`
- CORS restricted to domain-specific origins (not wildcard)
- CORS methods limited to `GET`, `HEAD`, `OPTIONS` (read-only)

**AKS Service Principal**
- Uses Network Contributor role (broad permissions)
- Recommended: Migrate to system-assigned managed identity
- Password rotation disabled via `ignore_changes` (security risk)

**Credentials in Commands**
- Storage account keys passed via environment variables, not command-line arguments
- Prevents exposure in process listings and shell history

**SAS Tokens**
- Hardcoded SAS tokens removed from Terraform variables
- Must be provided by user (marked as sensitive)

### General Security

**Secrets Management**
- All sensitive outputs marked with `sensitive = true`
- Rclone config files created with `0600` permissions
- Never commit credentials to version control

**CORS Configuration**
- Restricted to specific domains, not wildcard origins
- Response headers limited to essential headers only
- Methods restricted to read operations for public buckets

**Default Users**
- Change default passwords immediately after installation
- Default accounts are for initial setup only
- Use "Forgot Password" or create new users via API

## Development Workflow

When adding new cloud provider support or modifying building blocks:

1. Test Terraform modules independently before integrating
2. Use `helm template` to validate chart rendering
3. Test with minimal resource allocations first (see `global-resources.yaml`)
4. Ensure cloud-specific conditionals cover all providers
5. Update `images.yaml` when changing service versions
6. Document any new required variables in `global-values.yaml`
7. Follow security best practices documented above
